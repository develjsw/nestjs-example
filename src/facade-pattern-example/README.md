### 퍼사드 패턴 ( Facade Pattern )

- 퍼사드 패턴이란 ? :
  - 구조적 디자인 패턴으로, 복잡한 서브시스템 ( 모듈, 클래스, API 등 ) 에 대한 간단한 인터페이스를 제공하여 클라이언트가 복잡성을 숨기고 쉽게 시스템을 사용할 수 있도록 도와줌 
  - 즉, `여러 클래스나 메서드`를 `조합`한 복잡한 기능을 `하나의 간단한 인터페이스로 캡슐화`함


- 특징 :
  - 복잡성 숨김 : 클라이언트가 서브시스템의 세부 구현을 몰라도 동작 가능
  - 일관된 인터페이스 : 복잡한 작업을 간단한 메서드 호출로 대체
  - 의존성 감소 : 클라이언트와 서브시스템 간의 직접적인 의존성을 줄임


- 구조 :
  - `Facade` : 복잡한 서브시스템을 캡슐화하고 간단한 인터페이스를 제공
  - `Subsystem` : 실제 기능을 수행하는 클래스들로, 클라이언트가 직접 접근하지 않음
  - `Client` : 서브시스템에 직접 접근하는 대신 Facade를 사용함


- 사용시기 :
  - 시스템이 너무 복잡할 때
  - 간단한 인터페이스를 통해 복잡한 시스템을 접근하도록 하고 싶을때
  - 외부 결합도가 너무 높을 때 의존성을 낮추기 위해


- 장점 :
  - `복잡성 감소` : 서브시스템의 복잡한 로직을 숨기고, 단순한 인터페이스 제공
  - `유지보수성 향상` : 서브시스템 변경 시 퍼사드만 수정하면 클라이언트 코드는 수정하지 않아도 됨
  - `재사용성 증가` : 퍼사드 클래스는 특정 작업을 캡슐화하여 다른 컨텍스트에서도 쉽게 재사용 가능
  - `의존성 감소` : 클라이언트와 서브시스템 간의 직접적인 의존성을 줄임


- 단점 :
  - `추가 레이어 부담` : 퍼사드 클래스가 단순한 기능만 제공하면 오히려 불필요한 복잡성을 초래함
    - EX) 퍼사드가 단순히 서브시스템 호출만 전달하는 "중개인" 역할에 그치면 필요 없는 복잡성이 생김
  - `서브시스템 종속성` : 퍼사드가 없으면 서브시스템이 제대로 동작하지 않도록 설계되면 문제가 됨
    - EX) 모든 작업이 퍼사드를 통해서만 가능하게 설계되면, 퍼사드에 문제가 생길 경우 서브시스템도 사용할 수 없게 됨
  - `확장성 제한` : 퍼사드가 서브시스템의 일부 기능만 노출하도록 설계되면, 다른 중요한 기능은 클라이언트에서 사용할 수 없게 됨
    - EX) 서브시스템에 업데이트 기능이 있지만, 퍼사드가 등록 기능만 제공하면 클라이언트가 업데이트를 사용하지 못함
